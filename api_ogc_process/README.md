# OGC API - Processes v2 flask-ogc-process  FOP

## Overview

This project implements a standards-compliant web service conforming to the **OGC API - Processes** specification (version 1.0). The API provides a RESTful interface for executing geospatial and data processing tasks, with support for both synchronous and asynchronous execution models. The service is designed to facilitate interoperability in distributed computing environments through adherence to Open Geospatial Consortium (OGC) standards.

### Key Features

- **Standards Compliance**: Full implementation of OGC API - Processes 1.0 specification
- **Dual Execution Modes**: Support for synchronous (immediate) and asynchronous (deferred) process execution
- **Job Management**: Persistent tracking of process execution states with UUID-based identification
- **Schema Validation**: Automatic input/output validation using Pydantic models
- **Concurrent Processing**: Thread-pool-based execution for handling multiple simultaneous requests
- **Web Interface**: HTML-based user interface for process discovery and job monitoring
- **Extensible Architecture**: Modular design facilitating addition of custom processes

## Technologies

### Core Framework

- **Flask** (v3.x): Lightweight WSGI web application framework
- **OpenAPI 3.0**: Per-process spec generated by looping over the injected registry, served with an interactive Swagger UI at `/api`

### Data Processing & Validation

- **Pydantic** (v2): Runtime type checking and data validation with JSON Schema generation

### Persistence

- **sqlite3** (standard library): Autonomous default job store (`SQLiteJobStore`), no ORM required

### Additional Libraries

- **requests**: HTTP client for resolving inputs passed by reference

### Standards & Protocols

- **OGC API - Processes 1.0**: Core specification for process execution
- **JSON Schema**: Input/output schema definition
- **Schema.org**: Structured metadata for service description

## Installation

### Prerequisites

- Python 3.8 or higher
- pip (Python package installer)
- git (optional, for version control)

### Step 1: Clone or Download Repository

----

### Step 2: Create Virtual Environment

Creating an isolated Python environment prevents dependency conflicts with system packages.

```bash
python3 -m venv venv
source venv/bin/activate  # On Windows: venv\Scripts\activate
```

### Step 3: Install the Package

Install the package in editable mode - dependencies are declared in `pyproject.toml`
and pulled in automatically:

```bash
pip install -e .
# with the test suite:
pip install -e ".[test]"
```

This installs the engine's only runtime dependencies:
- `flask`
- `pydantic`
- `requests`

(`requirements.txt` is kept as a thin `-e .` pointer for tooling that expects it.)

### Step 4: Configure the Application

Configuration is **injected**, not global. Any missing key falls back to
`DefaultConfig` in `flask_ogc_api_processes/config.py`. You can pass a plain dict or any object with
the relevant attributes:

```python
from flask_ogc_api_processes import create_app

config = {
    "APP_TITLE": "Your API Title",
    "URL_PROJET": "https://your-domain.com",  # base URL used to build links
    "SECRET_KEY": "your-secure-secret-key",   # IMPORTANT: change in production
    "THREAD_NUMBER": 2,                        # concurrent async executions
}

app = create_app(config=config)
```

The same `config=` argument works on `create_ogc_blueprint(...)` when embedding the
engine. Recognised keys: `APP_TITLE`, `URL_PROJET`, `SECRET_KEY`, `THREAD_NUMBER`
(plus an optional `SERVICE_INFO` dict to fully override the landing document).

For the standalone demo you can simply edit the defaults in `flask_ogc_api_processes/config.py`. The
default job store persists to `flask_ogc_api_processes/job_store_data/` - no database URI to configure.

### Step 5: Initialize Database

No manual step is required. The default `SQLiteJobStore` creates its schema on instantiation and stores its database plus result files under `flask_ogc_api_processes/job_store_data/` (gitignored, configurable via `SQLiteJobStore(db_path=..., results_dir=...)`).

### Step 6: Run the Application

```bash
python run.py
```

The application will be accessible at `http://localhost:5000/`

## API Endpoints

### Core Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/` | Landing page with service metadata |
| GET | `/conformance` | OGC conformance classes |
| GET | `/processes` | List all available processes |
| GET | `/processes/{process_id}` | Retrieve process metadata and schema |
| POST | `/processes/{process_id}/execution` | Execute a process (sync/async) |
| GET | `/jobs` | List all jobs |
| GET | `/jobs/{job_id}` | Retrieve job status |
| GET | `/jobs/{job_id}/results` | Retrieve job results |
| DELETE | `/jobs/{job_id}` | Dismiss/cancel a job (terminates the process, keeps a `dismissed` record) |
| DELETE | `/jobs/{job_id}/purge` | Custom (non-OGC): hard-delete a job - remove its DB row and result file |

### Execution Modes

The request body follows the OGC execute schema: inputs go under an `inputs` object
(and optional `outputs` / `response` for output filtering).

**Synchronous Execution** (default):
```bash
curl -X POST http://localhost:5000/processes/buffer/execution \
  -H "Content-Type: application/json" \
  -d '{"inputs": {"x": 10, "y": 20, "name": "test"}}'
```

**Asynchronous Execution** (`Prefer: respond-async`):
```bash
curl -X POST http://localhost:5000/processes/buffer/execution \
  -H "Content-Type: application/json" \
  -H "Prefer: respond-async" \
  -d '{"inputs": {"x": 10, "y": 20, "name": "test"}}'
```

Returns **HTTP 201** with a `Location` header pointing at `/jobs/{job_id}`, a `Link`
header, and a `statusInfo` body (`status: "accepted"`). Poll `/jobs/{job_id}` for
status and fetch `/jobs/{job_id}/results` once `successful`.

## Adding a New OGC Process

### Process Architecture

Each OGC process is implemented as a Python class with the following components:

1. **Metadata Dictionary**: OGC-compliant process description
2. **Input Schema**: Pydantic model defining required and optional inputs
3. **Output Schema**: Pydantic model defining process outputs
4. **Execution Method**: Class method containing process logic

### Step-by-Step Implementation

#### Step 1: Create Process File

Create a new Python file for your process class. For the standalone/demo app put it
in `flask_ogc_api_processes/ogc_process/` (e.g. `my_custom_process.py`); when embedding the engine in
your own application, put it anywhere in **your** package - process classes are
injected, not imported by the engine.

#### Step 2: Define Process Class

A process class is **self-contained** and must not depend on any global config:
`metadata` carries only static, self-descriptive values, so the same class works in
any host regardless of its configuration.

```python
from pydantic import BaseModel, Field

class MyCustomProcess:
    """
    Description of what this process does.
    """

    # OGC Process Metadata
    metadata = {
        "id": "my-custom-process",  # Unique identifier (lowercase, hyphenated)
        "version": 1,
        "title": "My Custom Process",
        "description": "Detailed description of process functionality",
        "keywords": ["keyword1", "keyword2", "OGC"],
        "links": [{
            "type": "text/html",
            "rel": "about",
            "title": "Documentation",
            "href": "https://example.org/processes/my-custom-process",  # static, self-descriptive
            "hreflang": "en-US"
        }],
        "jobControlOptions": [
            "sync-execute",   # Synchronous execution support
            "async-execute"   # Asynchronous execution support
        ],
        "outputTransmission": [
            "value"  # Results transmitted as JSON values
        ]
    }

    # Input Schema (Pydantic Model)
    class Schema(BaseModel):
        # Required parameter (no default value)
        input_param1: str = Field(
            ...,  # Required
            title="Parameter 1",
            description="Description of parameter 1",
            examples=["example_value"]
        )

        # Optional parameter (with default)
        input_param2: int = Field(
            42,  # Default value
            title="Parameter 2",
            description="Description of parameter 2",
            examples=[100],
            ge=0  # Validation: greater than or equal to 0
        )

        # Nullable parameter
        input_param3: str | None = Field(
            None,
            title="Parameter 3",
            description="Optional parameter 3"
        )

    # Output Schema (Pydantic Model)
    class OutputSchema(BaseModel):
        result_value: str = Field(
            ...,
            title="Result",
            description="Description of the result"
        )
        status_code: int = Field(
            ...,
            title="Status Code",
            description="HTTP status code"
        )

    @classmethod
    def run(cls, validated_data: "MyCustomProcess.Schema"):
        """
        Execute the process logic.

        Args:
            validated_data: Validated input data (Schema instance)

        Returns:
            tuple: (result_dict, http_status_code)
        """
        try:
            # Access validated input parameters
            param1 = validated_data.input_param1
            param2 = validated_data.input_param2
            param3 = validated_data.input_param3

            # Process logic here
            result = {
                "result_value": f"Processed: {param1}",
                "status_code": 200
            }

            return result, 200

        except Exception as e:
            # Error handling
            return {"error": str(e)}, 500

    @classmethod
    def get_metadata(cls):
        """Return process metadata."""
        return cls.metadata
```

#### Step 3: Register Process by Injection

Processes are **injected** into `create_ogc_blueprint(processes, ...)` - you never edit
the engine's routes. Pass either a list (the engine keys it by `metadata["id"]`) or a
dict `{id: ProcessClass}`. Pick the option matching how you run the engine:

**A. Standalone / demo app** - add your class to the registry (the single place
that lists the demo processes):

```python
# flask_ogc_api_processes/ogc_process/registry.py
from .Example_OGC_Process import BufferProcess
from .hello_world import HelloWorldProcess
from .my_custom_process import MyCustomProcess          # your new module

EXAMPLE_PROCESSES = [BufferProcess, HelloWorldProcess, MyCustomProcess]  # add here
```

`create_app()` injects `EXAMPLE_PROCESSES` for you, so nothing else to change.

**B. Embedded in your own application** - inject your own registry when building the
blueprint (no dependency on `EXAMPLE_PROCESSES`):

```python
from flask_ogc_api_processes import create_ogc_blueprint
from myapp.processes import MyCustomProcess, AnotherProcess

bp = create_ogc_blueprint(
    [MyCustomProcess, AnotherProcess],   # your process registry
    config=my_config,                    # optional (falls back to DefaultConfig)
    job_store=my_job_store,              # optional (defaults to SQLiteJobStore)
    url_prefix="/ogc",                   # optional mount point
)
app.register_blueprint(bp)
```

Or pass the registry straight to `create_app(processes=[...])` if you only want the
standalone Flask app wired to your own processes.

#### Step 4: Test the Process

1. Restart the application
2. Verify process registration:
   ```bash
   curl http://localhost:5000/processes
   ```
3. View process metadata:
   ```bash
   curl http://localhost:5000/processes/my-custom-process
   ```
4. Execute the process (OGC execution endpoint is `/execution`):
   ```bash
   curl -X POST http://localhost:5000/processes/my-custom-process/execution \
     -H "Content-Type: application/json" \
     -d '{"inputs": {"input_param1": "test_value", "input_param2": 100}}'
   ```

### Advanced Process Features

#### Long-Running Processes

For processes that take significant time, report intermediate progress through the
injected job store's `update_job()` method:

```python
# The engine passes the active job store to async runs; report progress like this:
job_store.update_job(job_id, progress=25, status="running", message="Loading data")

# Perform some processing...
data = load_data(validated_data)

job_store.update_job(job_id, progress=50, status="running", message="Processing data")

# More processing...
result = process_data(data)

job_store.update_job(job_id, progress=75, status="running", message="Finalizing results")
```

**`update_job()` keyword parameters:**
- `job_id` (str, required): The UUID of the job to update
- `progress` (int, optional): Progress percentage (0-100)
- `status` (str, optional): One of `accepted`, `running`, `successful`, `failed`, `dismissed`
- `message` (str, optional): Human-readable state description

`update_job()` automatically sets the `started` timestamp the first time the status
becomes `running`, and the `finished` timestamp when it becomes `successful`,
`failed`, or `dismissed`.

**Note:** The framework automatically marks the job 100% complete and `successful`
when the process finishes. You only need to report intermediate progress.

**Location:** `update_job()` is defined on the `JobStore` interface and implemented by
`SQLiteJobStore` in `flask_ogc_api_processes/job_store.py`.

#### External Script Execution

For complex processes, separate logic into script files:

```python
# myapp/processes/scripts/my_process_logic.py
def execute_complex_operation(data):
    # Complex processing logic
    return processed_results

# myapp/processes/my_custom_process.py
from myapp.processes.scripts.my_process_logic import execute_complex_operation

class MyCustomProcess:
    @classmethod
    def run(cls, validated_data):
        result = execute_complex_operation(validated_data.model_dump())
        return result, 200
```

#### File Handling

For processes that accept or return files:

```python
import base64
from pydantic import BaseModel, Field

class Schema(BaseModel):
    file_content: str = Field(
        ...,
        title="File Content",
        description="Base64-encoded file content"
    )

@classmethod
def run(cls, validated_data):
    # Decode base64 file
    file_bytes = base64.b64decode(validated_data.file_content)

    # Process file...

    # Return result
    return {"status": "processed"}, 200
```

### Error Handling

Always return appropriate HTTP status codes:

- `200`: Success
- `400`: Bad Request (invalid input)
- `404`: Process not found
- `422`: Unprocessable Entity (validation error)
- `500`: Internal Server Error

Validation errors are handled automatically by Pydantic and the framework.

## Reusable package (`flask_ogc_api_processes`)

The engine ships as a **pip-installable, reusable package** (`flask_ogc_api_processes`). It can run
standalone **or** be embedded as a blueprint in any existing Flask app -
without colliding with a host package named `app`, and with **no import side
effects** (importing `flask_ogc_api_processes` creates no app, DB or config).

```bash
pip install .          # or: pip install -e .   for development
```

### Standalone

```python
# run.py
from flask_ogc_api_processes import create_app

app = create_app()     # Flask app: OGC API + OpenAPI spec / Swagger UI at /api
app.run()
```

### Embedded in a host application

The host injects its **own** process classes, config and (optionally) job store,
then protects execution with its own auth - the package imposes none.

```python
from flask_ogc_api_processes import create_ogc_blueprint
from my_project.processes import HOST_PROCESSES   # host-owned process classes

app.register_blueprint(
    create_ogc_blueprint(
        HOST_PROCESSES,
        config={"URL_PROJET": "https://my-host/api", "THREAD_NUMBER": 4},
        # job_store=...   # optional, see below
    ),
    url_prefix="/api",
)
```

**Config** may be a dict or any object exposing `APP_TITLE`, `URL_PROJET`,
`SECRET_KEY`, `THREAD_NUMBER` (and optionally `SERVICE_INFO`); anything omitted
falls back to `flask_ogc_api_processes.DefaultConfig`.

**Process contract** (unchanged): a class with a `metadata` dict, `Schema` and
`OutputSchema` (Pydantic `BaseModel`), a `run(cls, validated_data)` classmethod
and `get_metadata(cls)`.

### Pluggable job store

Job persistence lives behind the `flask_ogc_api_processes.JobStore` interface. The default,
`flask_ogc_api_processes.SQLiteJobStore`, is fully autonomous (raw `sqlite3` + JSON result files,
WAL-enabled for concurrent multi-process writers, picklable, and usable outside any
Flask context - required for the separate async job processes):

```python
from flask_ogc_api_processes import create_app, SQLiteJobStore

store = SQLiteJobStore(db_path="/var/lib/ogc/jobs.db", results_dir="/var/lib/ogc/results")
app = create_app(job_store=store)
```

To reuse a host's existing SQLAlchemy database instead, implement a small adapter:

```python
from flask_ogc_api_processes import JobStore

class SQLAlchemyJobStore(JobStore):
    def __init__(self, db, model):
        self.db, self.model = db, model
    def create_job(self, job_id, process_id, *, type="process",
                   status="accepted", message="", progress=0): ...
    def get_job(self, job_id): ...                 # -> OGC statusInfo dict | None
    def list_jobs(self, *, type=None, process_id=None, status=None,
                  limit=10, offset=0): ...          # -> (list[dict], total)
    def update_job(self, job_id, *, progress=None, status=None, message=None): ...
    def save_results(self, job_id, results): ...
    def load_results(self, job_id): ...            # -> dict | None
    # NB: update_job runs from a background thread - keep it Flask-context-free.
```
